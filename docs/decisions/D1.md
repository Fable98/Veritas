# ADR D1: Budget Enforcement Location, Safety vs. Liveness, and Revert Gas Bounds

- **Status**: Proposed
- **Date**: 2026-11-03
- **Invariants Touched**: INV-1, INV-4

## Context

In an autonomous agent spending protocol built on ERC-4337 and ERC-7579, budget limits must strictly prevent unauthorized expenditures across sequential and concurrent transactions. 

Under ERC-4337, transaction processing is decoupled into:
1. **Validation Phase (`validateUserOp`)**: Bundlers simulate validation off-chain before inclusion in a bundle. Under ERC-7562 validation rules, access to shared mutable state outside the sender account is strictly forbidden to prevent DoS attacks on bundlers. Validation cannot read or anticipate state mutations caused by other operations in the same bundle or across parallel bundlers.
2. **Execution Phase (`execute`)**: The EntryPoint invokes the smart contract account, executing calls and dispatching to installed execution hooks.

Any budget validation performed solely during `validateUserOp` would read stale ledger state under concurrency by design.

## Decision

1. **Execution-Time Hook Enforcement (Sole Safety Mechanism)**:
   - Budget limits are enforced strictly at execution time within an ERC-7579 execution hook (`MandateHook.preCheck` / `reserve`).
   - If a transaction would cause `committed + reserved + delegated > budget`, `MandateHook.preCheck` reverts the transaction during execution.
   - Budget checks are never implemented as the safety barrier in `validateUserOp`.

2. **Safety vs. Liveness Explicit Boundary**:
   - SDK pre-simulation and the per-mandate nonce key only buy liveness (fewer reverted ops, ordering), never safety. If anyone later weakens the hook check because “the SDK already checks”, INV-1 breaks.
   - The on-chain hook check is the single, non-negotiable safety invariant gate.

3. **Failed-Reservation Gas Drain Vector & Mitigations**:
   - *Attack Vector*: An attacker or prompt injection manipulating an agent to submit transactions that predictably fail the hook's reservation check causes the UserOp to pass validation but revert during execution. The account pays the bundler for execution gas, acting as a budget drain vector.
   - *SDK Policy Gate Cap (Benign / Prompt Misbehavior)*: The SDK policy gate tracks consecutive failed reservations per mandate and trips/pauses the mandate upon reaching a threshold (e.g., $K$ consecutive failures), alongside a per-mandate failed gas budget.
   - *Hard Upper Bound (Compromised Signer)*: The SDK policy gate bounds a well-behaved agent but cannot protect against a compromised signer path where private keys or signers bypass the SDK. In this adversarial scenario, the ultimate on-chain bound against draining is the smart account's native gas balance. Therefore, for v0, accounts must maintain a **small, dedicated gas balance** sized strictly for expected operational volume until paymasters are integrated.
   - *v1 Mitigation*: Introduce an ERC-4337 validating paymaster with postOp penalty logic, rate-limiting, and gas sponsorship quotas.

## Consequences

- **Positive**:
  - INV-1 (`committed + reserved + delegated <= budget`) is an inviolable on-chain safety property resistant to race conditions and concurrency.
  - Bundler validation rules (ERC-7562) are fully respected without requiring non-standard bundler modifications.
- **Negative**:
  - Reverting UserOps consume gas paid by the account.
- **Rejected Alternatives**:
  - *Validation-phase budget checking*: Rejected because ERC-7562 storage isolation makes validation checks against mutable shared budgets stale by design under concurrency.
