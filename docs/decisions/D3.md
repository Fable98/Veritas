# ADR D3: Delegation Model via Carve-Out, In-Flight Revocation, and Cascading Reclaim

- **Status**: Proposed
- **Date**: 2026-11-03
- **Invariants Touched**: INV-1, INV-2, INV-4, INV-8

## Context

Autonomous multi-agent systems require parent agents to delegate bounded spending authority to sub-agents (e.g., a orchestrator agent delegating to research, compute, and execution sub-agents).

Two primary delegation architectures exist:
1. *Shared-Pool Delegation*: Sub-agents spend against a shared pool governed by hierarchical quotas.
2. *Carve-Out Delegation*: Parent locks aside a discrete budget allocation into a dedicated child ledger.

Spend-time accounting in a shared pool requires traversing multiple ancestor ledgers and acquiring locks across contract hierarchies on every transaction. In a 26-week research build, this introduces unacceptable concurrency complexity and makes proving INV-4 challenging.

## Decision

1. **Carve-Out Model with Depth Bound 3**:
   - Carve-out is locked for v0 with a maximum delegation depth of 3 ($M_0 \to M_1 \to M_2 \to M_3$).
   - A child mandate can sub-delegate further if its current depth is $< 3$.
   - Shared-pool delegation is deferred to v1.

2. **Distinct `delegated` Ledger Field & INV-1 Restatement**:
   - To preserve INV-8 ("each reservation is finalized exactly once"), carve-out allocations are tracked under a dedicated `delegated` ledger field rather than overloading `reserved` (which is strictly reserved for escrow reservations).
   - Invariant INV-1 is formally stated per window $w$, including `delegated`:
     $$\forall w: \text{committed}_w + \text{reserved}_w + \text{delegated}_w \le \text{budget}_w$$
   - Available budget on any mandate is:
     $$\text{available} = \text{budget} - \text{committed} - \text{reserved} - \text{delegated}$$
   - When a parent delegates to a child, the allocation comes strictly out of the parent's `available` budget:
     $$\text{parent.delegated} \mathrel{+}= \text{child.budget}$$

3. **Child Windows vs. Parent Windows**:
   - For v0, child mandates receive a **per-lifetime carve-out budget** (a fixed, non-replenishing total allocation carved from the parent's current available budget).
   - Child budget does not automatically renew upon parent window rollover; parent mandates must explicitly grant fresh carve-outs or re-delegate.
   - Child validity must satisfy $\text{child.expiry} \le \text{parent.expiry}$.

4. **Strict Attenuation at Delegate Time and Effective-Limits Enforcement at Execution Time (INV-2)**:
   - A child mandate can never be wider than its parent. The contract strictly validates at `delegate()` time:
     - $\text{child.budget} \le \text{parent.available}$
     - $\text{child.expiry} \le \text{parent.expiry}$
     - $\text{child.perTxCap} \le \text{parent.perTxCap}$
     - $\text{child.targets} \subseteq \text{parent.targets}$
     - $\text{child.assuranceFloor} \ge \text{parent.assuranceFloor}$
   - **INV-2 hole — effective limits**: A parent may tighten its own parameters (expiry, perTxCap, targets, assuranceFloor) after `delegate()` has already been called. To close this gap, `preCheck` on a child mandate computes *effective limits* as the minimum (or intersection / maximum as appropriate) along the full ancestor chain at execution time:
     - $\text{effectivePerTxCap} = \min_{a \in \text{ancestors}} a.\text{perTxCap}$
     - $\text{effectiveExpiry} = \min_{a \in \text{ancestors}} a.\text{expiry}$
     - $\text{effectiveTargets} = \bigcap_{a \in \text{ancestors}} a.\text{targets}$
     - $\text{effectiveAssuranceFloor} = \max_{a \in \text{ancestors}} a.\text{assuranceFloor}$
   - Because the maximum delegation depth is 3, this ancestor-chain walk is **O(depth), bounded by 3**, not O(1). A child can therefore never exceed its parent's *current* limits at execution time, even if the parent tightened after delegation.

5. **`delegated` Across Rollover and Spend**:
   - `parent.delegated` carries across window rollover in the same way that `reserved` does: it is not reset at the rollover boundary. This reflects that the parent's liability to its children persists until those children are explicitly reclaimed.
   - The portion a child has actually spent (`child.committed`) is **never returned to the parent**. Only the child's unspent and unreserved capacity can return, and only via an explicit `reclaimChildBudget` call.

6. **Partial Reclaim**:
   - `reclaimChildBudget(childId)` returns exactly:
     $$\text{reclaimable} = \text{child.budget} - \text{child.committed} - \text{child.reserved} - \text{child.delegated}$$
   - It reduces `child.budget` by `reclaimable` and reduces `parent.delegated` by `reclaimable`.
   - It **reverts** (e.g., `ChildHasActiveDelegations`) only if the child still has unreclaimed sub-delegations (`child.delegated > 0`). Callers must reclaim leaf nodes first (depth 3, then depth 2, then depth 1).
   - It **never reverts** solely because of `Frozen` or `Revoked` status (mirroring INV-4).
   - It may be called **multiple times**: each call after in-flight escrows terminate (reducing `child.reserved`) releases the newly freed capacity to the parent.

   *Worked example*: Child C has `budget = 100`, `committed = 20`, `reserved = 30` (one in-flight escrow), `delegated = 0`.
   - First call: `reclaimable = 100 − 20 − 30 − 0 = 50`. `child.budget` becomes 50; `parent.delegated` decreases by 50.
   - Later, the in-flight escrow finalizes: `child.reserved` drops by 30, `child.committed` increases by 30 (or returns to available if refunded). `reclaimable` is now `50 − 50 − 0 − 0 = 0` (if committed) or `50 − 20 − 0 − 0 = 30` (if refunded). A second call releases any remaining idle capacity.

7. **Freeze Semantics**:
   - Under `Freeze` (Defensive Lock), the mandate is locked for new activity but in-flight operations must be allowed to terminate safely. The rationale is that a challenge uses a bond that is already reserved; blocking challenges would allow a fraudulent seller to win disputes by default, violating INV-5.
   - **Blocked under Freeze**: new `openEscrow`, new `delegate`, and any parameter-loosening proposals.
   - **Allowed under Freeze**: challenges (against existing escrows), `releaseBond`, escrow finalization, and `reclaimChildBudget`.

8. **Bounded, Non-Recursive Reclaim (Eliminating Unbounded Gas Loops)**:
   - Unspent child budget is reclaimed via an explicit call: `reclaimChildBudget(bytes32 childMandateId)`.
   - *Bounded Execution*: To prevent out-of-gas failures caused by unbounded child branching, the function operates strictly per-child and contains **no recursive loops**.
   - *Caller-Driven Bottom-Up Ordering*: If a child has active sub-delegations ($\text{child.delegated} > 0$), calling `reclaimChildBudget` on that child **reverts** (e.g., `ChildHasActiveDelegations`). Callers/keepers must reclaim leaf nodes first (depth 3, then depth 2, then depth 1).
   - *Safety on Frozen*: Reclaim must **never revert on `Frozen` status**, ensuring funds cannot be permanently locked.

9. **Revocation-Mode Proposed Semantics (Task 2.5)**:
   The operational semantics of the three revocation modes are defined across four axes:

   | Mode | New Escrows | In-Flight Escrows | Challenges | Reclaim Timing |
   |---|---|---|---|---|
   | **Complete** (Graceful Drain) | Prohibited immediately | Proceed through normal lifecycle to completion (delivery, acceptance, and payout). | Allowed (bond already reserved). | Immediate reclaim of idle unreserved budget (`available`); escrowed funds return to parent progressively as each in-flight escrow completes. |
   | **Freeze** (Defensive Lock) | Prohibited immediately | Buyer agent discretionary actions (e.g. voluntary acceptance) are halted. Escrows terminate via automated verification, dispute resolution, or timeout claims (INV-4 holds: `finalizeReservation` never reverts). | **Allowed**: a challenge uses an already-reserved bond; blocking it would let the seller win by default (violating INV-5). | Unreserved budget reclaimed immediately. Escrowed funds return to parent upon terminal state. Reclaim never reverts on Frozen. |
   | **Unwind** (Active Offboarding) | Prohibited immediately | Actively exercises contractually permitted exit paths without violating INV-5 (e.g., triggers mutual seller cancellation/refund pre-delivery if supported, or claims delivery timeouts as soon as deadlines pass). Does not unilaterally seize funds. | Allowed (bond already reserved). | Unreserved funds reclaimed immediately; cancelled/timed-out escrows return funds to parent upon terminal state. |

## Consequences

- **Positive**:
  - Spend-time accounting touches only the child mandate's ledger.
  - `preCheck` effective-limit walk is O(depth), bounded by 3: constant in practice, with no unbounded traversal.
  - Decoupling `delegated` from `reserved` cleanly preserves INV-8.
  - Per-child partial reclaim eliminates unbounded loop gas griefing and allows incremental recovery as in-flight escrows settle.
  - Freeze semantics preserve dispute liveness (INV-5) while preventing new liabilities.
- **Negative**:
  - `preCheck` is O(depth) rather than O(1); at depth 3 this is a fixed overhead of at most 3 ancestor reads.
  - Reclaiming deeply nested delegation trees requires multiple caller-driven transactions ordered bottom-up.
- **Rejected Alternatives**:
  - *Recursive subtree traversal*: Rejected due to unbounded gas consumption with arbitrary child branching factors.
  - *Shared-pool delegation*: Rejected for v0 due to cross-contract locking and verification complexity.
  - *O(1) preCheck without ancestor walk*: Rejected because it leaves INV-2 open to post-delegation parent tightening (INV-2 hole).
